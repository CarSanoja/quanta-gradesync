# Cloud Run deployment and triggered end-to-end run — 2026-08-19

First execution of the full pipeline on deployed infrastructure. The trigger was
a file upload: no HTTP call was made by hand. Chain exercised end to end:
`gcloud storage cp` → GCS `OBJECT_FINALIZE` → Pub/Sub topic → push subscription
with OIDC → Cloud Run → Gemini on Vertex → Firestore → SIS sink.

## Problems found and fixed during the deployment

| # | Symptom | Cause | Fix |
|---|---|---|---|
| 1 | `gcloud builds submit` failed: source object access denied | Cloud Build runs as the Compute default service account by default | Dedicated `gradesync-builder` service account with least-privilege roles, pinned in `cloudbuild.yaml` |
| 2 | `gcloud run deploy` rejected `--set-env-vars`: invalid delimiter | The shipped config used a malformed `^^^` custom delimiter that had never been executed | Plain comma-separated list; no value contains a comma |
| 3 | Deploy denied `iam.serviceaccounts.actAs` on `autocurricula-runner@${PROJECT_ID}...` | `${PROJECT_ID}` is not expanded inside user-defined substitutions | Literal project id in the substitution values |
| 4 | Every push delivery returned 403 at the Cloud Run edge | The webhook only read the shared token from the `Authorization` header, which Pub/Sub OIDC already occupies with its JWT | Accept the token from a `token` query parameter as well; OIDC keeps the header. Three tests added |
| 5 | Push deliveries still 403 after the token fix | Default OIDC audience includes the endpoint query string | `--push-auth-token-audience` pinned to the service URL |
| 6 | Job reached `fetched` and then stalled indefinitely | The webhook acknowledges immediately and runs the pipeline in a background task; Cloud Run throttles CPU once the response is sent | Deploy with CPU always allocated (`--no-cpu-throttling`) |

Finding 6 is architectural, not cosmetic: with request-scoped CPU the engine
acknowledges work it then cannot perform, and because the delivery was already
acknowledged Pub/Sub never retries it. The current fix keeps the fire-and-forget
design and pays for allocated CPU. The alternative — awaiting the pipeline inside
the request and acknowledging only on success — would restore Pub/Sub retry
semantics for free and is the recommended follow-up; batch wall clock (~44 s)
fits comfortably inside both the 600 s ack deadline and the 900 s request
timeout.

## Public access

`--allow-unauthenticated` cannot be applied: the organization policy on
`somosquanta.com` (domain restricted sharing) refuses an `allUsers` binding, so
the deployment is invoke-restricted to authorized principals. Pub/Sub ingestion
is unaffected because it authenticates with OIDC. Serving the console to
external reviewers requires either a project-level exception to that
organization policy or an authenticated proxy; the decision is pending.
